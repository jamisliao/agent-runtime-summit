01｜自己刻 Agent 框架，最難的不是呼叫 LLM

原01頁；圖內編號01

重點、講稿與轉場
  • Tool Loop 能讓模型呼叫工具，但還不足以承接真實任務。
  • 今天沿著實作遇到的問題，說明如何走到可交付的 Runtime。

我一開始只想讓模型反覆呼叫工具。真的接上企業流程後，才陸續遇到漏步驟、錯誤結論與難以追查的問題。今天用這些經驗，說明循環之外需要哪些執行責任。

接下一頁：先看我一開始以為的 Agent 長什麼樣。

02｜這個 Tool Loop，幾行程式碼就能跑起來

原02＋03頁；圖內編號02

重點、講稿與轉場
  • 模型要求工具時才執行；結果交回 Context，繼續問模型。
  • 最小循環確實能跑，但還沒承接真實任務的責任。

LLM 是理解文字、判斷下一步的模型；Tool 是查資料或執行操作的程式。我最初的做法很簡單：呼叫模型，模型要求工具就執行，把結果 append 回 Context，再問一次；模型交出答案就結束。這幾行概念碼真的可以跑起來，所以當時我以為主要工作完成了。但這只是最小循環，還沒處理真實任務需要的可靠性。

接下一頁：直到它開始碰到真實任務：工具會動、模型會答，就代表可以交付嗎？

03｜你以為這樣就結束了嗎？

原04頁；圖內編號04

重點、講稿與轉場
  • 工具會動、模型會回答，只是 Demo 成功。
  • 企業任務可能沒有 exception，卻仍交出錯誤結果。

工具會動、模型會回答，很快就能看到。但一進企業流程，我開始遇到那些不會直接報 exception，卻會交出錯誤結果的問題。

接下一頁：這些問題，慢慢長成六項必須承接的責任。

04｜會動之後，六個問題攤開了

原05頁；圖內編號05

重點、講稿與轉場
  • 六個問題：給什麼資訊、怎麼完成流程、哪些錯不能放行。
  • 出錯如何追查、修改如何驗證、每次執行與測試的成本在哪裡。
  • 這是全場的問題地圖，最後會回扣整套 Runtime。

從資訊與流程開始，接著是哪些錯不能通過。出了問題，要能追查、驗證修改，也要付得起反覆測試的成本。等一下會依這些問題一路往下走。

接下一頁：在展開之前，先交代我為什麼選擇自己刻。

05｜為什麼選擇自己刻？

原06頁；圖內編號06

重點、講稿與轉場
  • 自己刻的理由：掌握模型替換、特殊流程與既有企業治理整合。
  • 這場聚焦單次任務的執行與驗證，不展開模型介接及跨 Session 記憶。

現成框架有價值。我自己刻，是希望掌握模型替換、特殊流程與既有治理整合。今天集中在一次任務怎麼執行與驗證，模型介接細節和跨 Session 記憶另外再談。

接下一頁：所以我決定自己把這個 Runtime 接起來。最初就是前面那個循環：模型選工具、工具執行、結果交回模型。接著，第一個需要我做決定的地方出現了：工具回來的這一大包資料，該怎麼交回去？

06｜第一個問題：工具結果，怎麼交回模型？

原07頁；圖內編號07

重點、講稿與轉場
  • 回到 Tool Loop：工具已經執行完，結果要怎麼交回模型？
  • Context 是這一輪給模型看的內容，包含使用者要求、規則與工具資料。

先停在這個位置：工具已經執行完，現在要把結果交回模型。這一輪交給模型看的內容，就是 Context；裡面也包含使用者要求與任務規則。那工具回來的一大包資料，要怎麼放進去？

接下一頁：當時我的做法很直覺：工具回什麼，我就全部加進去。下一頁就是我最初的接法。

07｜每輪都 append，Context 越堆越多

原08＋09頁；圖內編號07

重點、講稿與轉場
  • 每輪直接 append，使舊結果、新結果與欄位持續累積。
  • 累積更多資料，不等於每一項都對下一步有用。

第一版工具回什麼，我就把它全部 append。一次回傳看起來很自然，幾輪之後，舊結果還在、新結果又加入，每份結果裡還有大量欄位。任務要求和流程規則也一起帶給模型。這不是說模型一定會忘記規則，而是每次呼叫都帶上更多內容，卻還沒判斷它們對下一步是否有用。

接下一頁：不再每輪全部append後，完整工具結果要放哪裡？下一頁先交代資料如何保存，再決定這輪給模型什麼。

08｜工具結果留完整，給模型的內容按需準備

原10＋11頁；圖內編號08

重點、講稿與轉場
  • 先保存工具的原始完整結果，後續工具仍可取用。
  • 給模型的本輪Context按下一步需要準備，不等於把資料全部塞入。

工具回傳一大包結果時，我不會因為模型這一輪只需要其中一部分，就把其餘資料丟掉。這個Runtime會先保存原始完整結果，因為後續工具可能還需要取用完整資料；再依下一步用途，準備這一輪給模型看的內容。資料不是一开始就在資料庫裡，是工具回傳後，由Runtime刻意留下來的。完整保存和全部塞進Context是兩件不同的事；這是本案例的設計選擇，不是所有工具都會自動入庫。

接下一頁：用分析Log的實際場景來看：工具一查，就可能回來一大包原始紀錄。

09｜要分析 Log，卻查回一大包原始紀錄

原12頁；圖內編號12

重點、講稿與轉場
  • 用分析系統 Log 當例子：工具查回一大包原始紀錄。
  • 模型要讀相關 Log 才能找線索，但不必直接讀完整包。

假設我請 Agent 分析一段時間的系統 Log。工具查回來的可能是一大包原始紀錄。下一步要分析問題，模型確實需要讀到相關內容，不能完全不給它看；但也不能只因為工具回來了，就把整包資料原封不動塞進 Context。這個案例要問的第一件事是：這次的問題，需要模型看哪些 Log？

接下一頁：先把這次的問題釐清，再決定原始 Log 要怎麼整理給模型。

10｜分析 Log，先挑出這次需要的內容

原13頁；圖內編號13

重點、講稿與轉場
  • 依問題縮小時間範圍、挑必要欄位，或分類取代表片段、做摘要。
  • 這些是可選方法，不是固定四步；原始 Log 仍留在系統可供追查。

回到剛剛的 Log 分析任務：如果問題只涉及某段時間，就先縮小時間範圍；分析只用得到部分欄位，就保留那些欄位；有許多重複紀錄時，可以分類後取代表片段，需要時再做摘要。這些做法依問題選用，不是每次都必須做完四步。原始 Log 仍保留在系統，後續需要細節時能再查。這就是把「下一步需要什麼」落實到工具結果的整理。

接下一頁：還有另一種情況：下一個操作根本不需要模型讀懂整包資料。

11｜模型傳 Ref，工具取完整資料

原14＋15頁；圖內編號11

重點、講稿與轉場
  • 模型接收狀態和 Ref，資料搬運由工具與系統處理。
  • 取件請求與完整資料回傳分開；Ref 的使用權限仍由系統檢查。

上一頁是模型需要閱讀的 Log。另一種情況是 API 回傳很大，但下一步只需要判斷成功與否，再把資料交給另一個工具。這時 Tool A 把完整結果存進系統，交給模型的是 status 和 data_ref。模型選好下一步，Tool B 在服務端依 Ref 取回完整資料；大腦看燈號，管線傳重貨。Ref 是取件參照，不是權限，能不能讀、允許做什麼，仍由系統檢查。

接下一頁：Ref 減少模型需要閱讀的內容，不只是省 Token。即使 Context 還沒滿，增加負擔也可能讓流程跑偏。

12｜Context 越重，越吃模型能力

原16頁；圖內編號16

重點、講稿與轉場
  • Context 裡的資料、規則與流程狀態越多，模型要同時顧到的事情越多。
  • 即使沒超過容量上限，同一模型也可能漏步驟或提早停止。

Context 裡放得越多，模型就要同時顧到越多資料、規則、工具結果與流程狀態。問題不只是 Token 有沒有超過上限，而是這個模型還能不能在這個負載下守住整套 Workflow。原本能完成任務的輕量模型，Context 變重後可能開始漏看規則、跳過步驟或提早停止。

接下一頁：接下來看同一個 Workflow 的實測：Context 從 10k 增加到 30k 後，原本的 MoE 模型發生什麼事？為什麼最後必須換成更大的 Dense 模型？

13｜30k Context，迫使我換成更大的模型

原17頁；圖內編號17

重點、講稿與轉場
  • 同一組測試：26B-A4B MoE 在 10k 成功 9/10，30k 降為 4/10。
  • 30k 換成 31B Dense 後成功 9/10，呈現 Context 負載推高模型需求的觀察。
  • 每組只有十次，不是通用模型排名，也不能把所有失敗都歸因於長度。

在同一 Skill、測資、Tool 與 temperature 下，gemma-4-26b-a4b-it-mlx 在 10k Context 成功九次，增加到 30k 後只成功四次；同樣是 30k，換成 gemma-4-31b-it 後又成功九次。失敗時會跳過 summary builder、漏掉 warning 或提早停止。這不是要證明 31B 永遠比較好，而是說明：Context 沒有控制好，原本較輕的模型可能撐不住同一套 Workflow，最後只能用更重的模型補足。這是每組十次的有限觀察，不作通用排名，也不把所有失敗都歸因於長度。

接下一頁：但升級模型不是唯一解法。若 Runtime 先把 Working Context 控制好，還需要一開始就付出更大模型的成本嗎？

14｜Context 管理會影響需要多大的模型

原18頁；圖內編號18

重點、講稿與轉場
  • 升級模型不是唯一選項，先整理 Working Context，再用原模型重跑。
  • 若原模型已能穩定完成，就不必先付出升級的推論成本。
  • 目前數據尚未證明整理後一定恢復；速度也受硬體、量化與框架影響。

換成 31B Dense 可以把這組測試的完成次數拉回來，但代價通常是更高的推論負擔，而且實際速度仍會受到硬體、量化與推論框架影響。另一個應先驗證的選項是整理 Context：完整資料留在 Runtime，只把這一步需要的內容、狀態與控制訊號交給模型。現有數據沒有直接證明整理後的 26B-A4B 一定能恢復，因此正確做法是用原模型重跑同一個任務；如果已能穩定完成，就不必先升級模型。Context Management 不只是省 Token，也可能降低完成任務所需的模型能力與算力。

接下一頁：那麼，整理到什麼程度才算有效？判斷標準不能只是 Token 變少，而是同一個任務仍能穩定完成。

15｜Working Context 不是越短越好

原19頁；圖內編號19

重點、講稿與轉場
  • Working Context 要留下完成下一步所需的資訊，不是刪到最少。
  • Token 減少是手段，同一任務能穩定完成才是驗收標準。

Context Management 的目標不是把內容刪到最少，而是留下完成下一步需要的資訊，同時移除不必交給模型的負擔。最後仍要看指定模型能不能在同一個任務裡守住規則並完成 Workflow。Token 變少只是手段，任務能穩定完成才是驗收標準。

接下一頁：要確認整理前後是否真的改善，就要用同一個任務重跑，並留下每次 Run 的條件與結果。

16｜怎麼證明整理 Context 有幫助？

原20頁；圖內編號20

重點、講稿與轉場
  • 固定 Skill、測資、Tool 與 temperature，一次只改一個條件並重跑。
  • 同一 Run 記錄模型、Context tokens、完成結果與失敗型態。
  • 才能區分改善來自 Context 整理、模型升級，還是其他變動。

只說模型怪怪的，無法判斷 Context 整理有沒有幫助。要固定 Skill、測資、Tool 與 temperature，用同一個任務重跑，並把模型、Context tokens、完成結果與失敗型態放在同一次 Run 裡。一次只改一個條件，才知道改善來自 Context 整理、模型升級，還是其他變動。Token 同時是成本紀錄與工作負載線索，後面談成本時會再回來。

接下一頁：即使驗證後確認資訊已經足夠，Context Management 仍只能決定模型看到什麼；它不能保證必要步驟一定被執行。

17｜資訊給對了，流程仍可能走錯

原21頁；圖內編號21

重點、講稿與轉場
  • 延續 Log 案例：資訊準備好，模型能開始分析，不代表任務已交付。
  • 終點是一份有指定分類、warning、統計與明細的正式報告。

到這裡，Context Management 已經把這次分析需要的 Log、規則與狀態準備好，模型也能開始分析差異。但這個任務的終點不是一段分析文字，而是一份正式報告。報告必須包含指定的分類、warning、統計與明細。資訊準備完成，只代表模型看得到需要的材料；交付流程還沒有完成。

接下一頁：既然任務還有一段正式交付流程，下一個問題就是：流程寫進 Skill 之後，模型是否每次都會照著完成？

18｜流程寫進 Skill，模型真的會照做嗎？

原22頁；圖內編號22

重點、講稿與轉場
  • Skill 用自然語言寫明步驟、停止條件與輸出格式。
  • 一次成功只能證明這次成功，不能證明模型會穩定照 SOP 做。

Context 準備好之後，模型已經看得到相關 Log、任務規則與目前狀態。接下來的問題是，它會不會照 Skill 把流程完成。我一開始以為，只要把第一步、第二步、停止條件與輸出格式寫清楚，模型就會照著走。但一次執行成功，只能證明這一次有成功，還不能證明流程穩定。

接下一頁：要看見這種不穩定，不能只挑一個成功案例，而要固定條件反覆執行同一個任務。

19｜同一個任務，多跑幾次才看得出問題

原23頁；圖內編號23

重點、講稿與轉場
  • 固定同一版 Skill、測資、Tool 與模型設定，重跑同一 Scenario。
  • 排除不同案例的干擾，觀察必要步驟是否能穩定完成。

我用 LLM Evaluation 固定同一版 Skill、同一組測資、同一個 Tool 與同一組模型設定，再讓同一個 Scenario 重跑多次。這樣才能排除案例不同造成的干擾，觀察模型在相同條件下，是否每次都走完相同的必要步驟。

接下一頁：當同一個任務重跑多次，問題才真正浮現：答案都有產生，執行過程卻不一致。

20｜答案都有產生，執行路徑卻不一樣

原24頁；圖內編號24

重點、講稿與轉場
  • 有些 Run 跳步、順序錯、提早停止或繞過 fallback，仍有合理的 Final Answer。
  • 不能只評最後文字；要把實際路徑與預期流程一起比較。

重跑後我看到的不是單純答對或答錯。有些 Run 正常完成，有些跳過必要 Operation，有些順序錯誤、提早停止，或者繞過 fallback。麻煩的是，它們最後常常都會產生一段看起來合理的 Final Answer。如果 Evaluation 只看最後文字，就會把流程錯誤當成成功。

接下一頁：其中一個最典型的失敗，是模型跳過固定的 Summary Builder，自己交出摘要。

21｜跳過 Builder，摘要有了，交付卻沒完成

原25＋26頁；圖內編號21

重點、講稿與轉場
  • 有答案、沒有 exception，仍可能漏掉必要 Builder。
  • 固定格式與必要資訊是交付要求，不是可自由省略的步驟。

Skill 已經要求分析差異後呼叫 build_execution_summary，但某些 Run 會跳過 Builder，由模型自行摘要。它沒有 exception，畫面也有答案；對照路徑才看到必要 Operation 沒發生。Builder 用來收斂固定格式、完整分類、必要 warning、統計與明細，模型自由摘要則可能漏掉指定交付。這裡的問題不是文字通不通順，而是任務要求的交付是否完成。

接下一頁：因此 Evaluation 不能只看答案，還要看必要操作是否真的發生，再透過重跑觀察穩定性。

22｜多跑幾次，檢查答案，也檢查步驟

原27＋28頁；圖內編號22

重點、講稿與轉場
  • 答案和必要操作要一起檢查，才能辨識看似成功的漏步驟。
  • 重複 Run 與多 Scenario 衡量目前樣本的遵守程度，不保證未來零錯誤。

Skill 仍然是給模型看的自然語言說明，不是一定會執行的程式。我會在相同條件下重跑，也用不同情境測試；對照 Skill 檢查最後答案是否符合要求，以及必要步驟是否真的做完。Evaluation 告訴我們這批測試有多常照做，讓修改有依據；不代表下一次執行不可能出錯。

接下一頁：通過率可以很高，甚至目前全部通過；但這仍是測試結果，不是未來每一次執行的保證。

23｜Evaluation 100%，仍然不是零風險

原29頁；圖內編號29

重點、講稿與轉場
  • Evaluation 衡量已覆蓋場景的表現，可用失敗案例持續降低錯誤。
  • 即使目前測試 100% 通過，也不保證未來機率模型永遠照 Skill 做。

Evaluation 做得越完整，我們越能知道模型在大部分場景中有多高的機率按照 Skill 執行，也能透過失敗案例持續修改 Skill、模型或 Context，降低觀察到的錯誤率。但 Skill 始終是自然語言說明，LLM 也始終是機率模型。即使 Evaluation 在目前案例中得到 100%，未來某次執行仍然可能不準，或者沒有按照 Skill 的說明做判斷。

接下一頁：因此下一個設計問題不是「Evaluation 還能不能再多做一點」，而是「這種錯誤偶爾發生一次，我能不能接受」。

24｜錯誤能不能放行？

原30頁；圖內編號30

重點、講稿與轉場
  • 可接受偶發錯誤：用 Skill 引導，再用 Evaluation 量測與改善。
  • 一次都不能接受的錯：交給 Guardrail 或 HITL 在系統邊界阻止放行。

這就是我的分界。可以接受偶發錯誤的，用 Skill 說明，再透過 Evaluation 量測與改善穩定度。如果某個錯誤一次都不能接受，就不能只期待 LLM 每次都遵守說明，而要用 Guardrail 或 HITL 把它擋在真正的系統邊界上。

接下一頁：先用三個具體例子，看看一條寫在 Skill 裡的規則，如何變成系統真正能檢查的條件。

25｜把不可接受的錯，變成可檢查的條件

原31頁；圖內編號31

重點、講稿與轉場
  • 不能算錯的日期交給 deterministic tool，不只提醒模型仔細。
  • 根因結論要查 Evidence；修改資料要由後端檢查 Authorization。
  • 把不可接受的錯落成實際檢查機制，不只停在文字規則。

如果日期不能算錯，就不要只在 Skill 裡提醒模型仔細計算，而是交給 deterministic tool。沒有 Evidence 不能宣稱根因，就要讓 Claim 在成為正式輸出前接受 Evidence Check。未授權不能修改資料，就要由後端根據使用者、資源與動作檢查 Authorization。共同原則是：不可接受的錯誤，不能只停留在自然語言說明。

接下一頁：這三個例子看起來不同，但底層其實是同一件事：LLM 可以提出結果，卻不擁有最後的放行權。

26｜LLM 可以提出，不能自己放行

原32頁；圖內編號32

重點、講稿與轉場
  • LLM 可提出 Tool Call、Claim 或操作建議，但不能自行宣告安全。
  • 格式、業務規則、Evidence、Authorization 與當下條件通過後，才能正式放行。

Skill 告訴 LLM 應該怎麼做；Guardrail 改變的是最後的決定權。LLM 可以提出 Tool Call、形成 Claim，或者建議一個操作，但不能自己宣告它們已經安全。Tool Call 要先符合格式與業務規則，Claim 要有 Evidence 支持，實際操作則要通過 Authorization 與當下條件。只有檢查通過，提案才會成為正式輸出或產生實際影響。

接下一頁：回到前面分析 Log 的案例。當時我們處理的是要給模型哪些資料；現在看模型讀完後提出的根因結論，是否有足夠證據支持。

27｜查到錯誤，就能判定根因嗎？

原33頁；圖內編號33

重點、講稿與轉場
  • 回到 ELK Log 分析：現在討論結論的證據，不是哪些資料進 Context。
  • 查到錯誤、時間接近只是線索，不能直接證明根因。

回到前面的 ELK Log 分析。前面處理哪些內容該進 Context；現在改看模型讀完後下的結論。真實錯誤和時間接近只能提供線索，不自動證明根因，必須檢查支持關係。

接下一頁：證據只能支持可能性，就不能把它說成確定結論。

28｜證據不足，就不能說成確定結論

原34頁；圖內編號34

重點、講稿與轉場
  • 區分已觀察事實、待驗證假設與證據不足。
  • 允許提出推論，但不把沒有足夠支持的猜測包裝成確定結論。

時間接近可以成為調查線索，但還不能證明因果。若目前資料只能支持可能性，就把它保留為待驗證假設；若證據不足，就清楚說明還缺什麼。Evidence Boundary 要阻止的不是所有推論，而是沒有足夠支持卻被包裝成確定結論的輸出。

接下一頁：系統可以檢查規則與證據，但任務是不是使用者真正要的、某次操作是否允許，有些情況需要把決定交回給人。這不是讓人把證據不足的推測批准成事實。

29｜有些決定，不能讓 Agent 自己確認

原35頁；圖內編號35

重點、講稿與轉場
  • 系統查規則與證據；有些決定需要人確認意圖或批准操作。
  • 兩種人工責任不同，也不是請人替缺乏證據的結論背書。

前面談系統如何檢查規則和證據，但任務是不是使用者真正要的、某次操作是否允許，有些情況需要把決定交回給人。確認理解和批准操作是兩種不同責任，不是讓人為缺乏證據的結論背書。

接下一頁：先看任務開始前：讓使用者確認 Agent 理解的目標與範圍。

30｜先確認理解，避免做完錯誤的任務

原36＋37頁；圖內編號30

重點、講稿與轉場
  • 執行前先確認目標、排除與範圍，避免後面成功完成錯任務。
  • 意圖確認不是操作批准；兩者解決不同問題。

像「找 A 類、排除 B，只處理最近三天失敗項目」，同時包含目標、排除條件、時間範圍與狀態。先把 Agent 理解的內容整理成可閱讀的確認摘要，讓使用者確認、修改或退回，再依確認後版本開始。這裡是在確認有沒有理解對，不是在批准扣款或寫入。如果範圍一開始錯了，後面每個 Tool Call 都成功，仍可能完成錯誤任務。

接下一頁：確認理解以外，寫入、扣款或對外通知還需要另一種確認：批准這次操作。

31｜寫入、扣款或對外通知，執行前要先批准

原38頁；圖內編號38

重點、講稿與轉場
  • 寫入、扣款、開單或對外通知，系統要在執行前停下等批准。
  • 讓人先看懂提案、影響範圍與預覽，留下批准者、時間和批准版本。

寫入、開單、扣款或對外通知等高風險操作，不能只靠 Skill 裡一句「請先取得批准」。系統要停在人工 Gate 前，讓人看懂提案與影響範圍，再批准或拒絕。紀錄還要保留誰批准、何時批准，以及當時看到哪一份預覽。

接下一頁：即使人已經批准，真正執行前仍然不能直接沿用舊狀態。

32｜批准後，執行前仍要重新檢查條件

原39頁；圖內編號39

重點、講稿與轉場
  • 批准到執行可能相隔一段時間，資料、任務或權限狀態可能已變。
  • 執行前重新檢查 Precondition，將批准內容與檢查結果留在 Trace。

Approval 會把一次 Agent Run 切成提案與執行兩段，中間可能隔幾分鐘或幾小時。資料可能已被別人處理，任務可能已關閉，帳務或權限狀態也可能改變。因此批准不是永久通行證。Runtime 在真正執行前仍要重新檢查 Precondition，並把批准內容與檢查結果留在 Trace。

接下一頁：流程偏離、Guardrail 攔截與 HITL 決策都必須留下可追查的紀錄。下一章回到那份缺漏摘要，看看如何從 Trace 找出它在哪一步走錯。

33｜為什麼這次沒有呼叫 Builder？

原40頁；圖內編號40

重點、講稿與轉場
  • 回到模型跳過 Builder 的案例，切換到開發者追查視角。
  • 看 Agent 的執行紀錄、當時可見資料與 Skill 版本，不是業務系統的 ELK Log。

現在換成開發者的角度，回到先前模型跳過 Builder 自行摘要的案例。我們已知道漏了哪一步，接著看當次執行紀錄、可見資料和 Skill 版本來分析。這裡的紀錄是 Agent 的執行紀錄，不是前面拿來分析的業務 Log。

接下一頁：追查時，Log、Trace、Evidence 分別回答不同問題。

34｜做了什麼、怎麼走、憑什麼說？

原41頁；圖內編號41

重點、講稿與轉場
  • Operation Log 記錄做了什麼，Decision Trace 串起同次執行路徑。
  • Evidence Binding 連結結論的支持依據，三者用途不能混為一談。

這裡的 Log 是 Agent 自己的執行紀錄，和前面查業務系統 ELK 的用途不同。Log 記錄事件，Trace 把同次執行的路徑串起來，Evidence 支撐輸出的結論。

接下一頁：放回摘要案例，這些紀錄如何幫我們定位問題？

35｜追查漏步驟，要連回當時的 Run 與狀態

原42＋43頁；圖內編號35

重點、講稿與轉場
  • 同次 Run 先定位漏步驟，再追查停止時的狀態與規則。
  • 保留可見依據，不把它宣稱為內部思考或已證明根因。

回到 Builder 漏步驟案例，把分析、摘要與停止事件連到同一次 Run，先定位 Builder 沒被呼叫。接著回看停止時的可見資料、當時狀態、Skill 規則和模型已輸出的理由。這些是可以保存與核對的追查依據，支持提出候選解釋；不等於模型內部思考，也不能直接說已找出根因。

接下一頁：其中最容易被忽略的一份依據，是當時那一版 Skill，而不是現在已修改的版本。

36｜歷史 Run，要綁定當時的 Skill

原44頁；圖內編號44

重點、講稿與轉場
  • 歷史 Run 要綁定當時 Skill 版本或 Hash，避免拿新版解釋舊行為。
  • 完整重建還需要對應資料、工具結果與執行環境，不只 Skill 版本。

Skill 可能一直被修改。若沒有版本或 Hash，就容易拿新版規則解釋舊 Run，無法歸因。版本綁定是必要條件，完整重建還需要對應資料、工具結果與執行環境紀錄。

接下一頁：找對當時的規則，才有辦法提出具體修改。

37｜從追查依據，提出候選修改

原45頁；圖內編號45

重點、講稿與轉場
  • 用 Trace 提出改善假設，例如補清楚必要 Builder 結果與停止條件。
  • 候選修改仍要測試；追查線索不能直接證明原案一定由那條規則造成。

例如停止條件若不夠明確，可以提出補上必要 Builder 結果的修改。這是教學示意的改善假設，不宣稱原案一定由這條規則造成。候選版本還要用測試證明。

接下一頁：那我們要測什麼，才知道 Agent 真的改善？

38｜驗證修改，要看整次任務

原46頁；圖內編號46

重點、講稿與轉場
  • Guard 在執行時攔截；Eval 在開發測試時驗證行為是否符合預期。
  • 修改後要看整次任務的結果、路徑與工具使用，不只最後答案。

現在是在開發測試中檢查 Agent。Guard 是執行時攔截，Eval 則檢查這次行為是否符合預期。結果、路徑、工具使用都要看，才能知道它是否用可靠方式完成。

接下一頁：先從使用者最後拿到的報告看起。

39｜報告，有沒有交付必要內容？

原47頁；圖內編號47

重點、講稿與轉場
  • Outcome Eval 看使用者收到的報告：格式、分類、必要 warning 是否完整。
  • 結論是否有依據，也是交付品質的一部分。

第一層是結果：格式對不對、分類是否完整、必要 warning 有沒有出現、結論是否有根據。這些是使用者真正收到的交付內容。

接下一頁：但報告剛好看起來正確，還不能證明流程走對了。

40｜答案像對的，路徑也要檢查

原48頁；圖內編號48

重點、講稿與轉場
  • Trajectory Eval 比對情境要求與實際路徑，確認必要操作是否發生。
  • 允許合法分支，但要找出漏步驟、順序錯、重複呼叫與提早停止。

這個情境要求呼叫 Builder，就要檢查它是否真的發生。其他流程可以有合法分支，依各自契約驗證。重點是抓到漏步驟、順序錯、重複呼叫或提早停止。

接下一頁：即使工具選對了，使用方式還可能出錯。

41｜呼叫了 Builder，傳入的資料也對嗎？

原49頁；圖內編號49

重點、講稿與轉場
  • 叫對 Builder 還不夠，要檢查參數和資料引用。
  • Ref 是否對應本次分析結果？必要參數與使用條件是否正確？

前一頁問該呼叫的工具有沒有發生。這一頁再往下看，傳入 Builder 的 Ref 是否對應本次分析結果，必要參數有沒有漏。工具名稱正確只是第一步，資料和使用條件也要正確。

接下一頁：這些檢查要怎麼實作？哪些直接用程式，哪些需要語意判斷？

42｜哪些檢查用程式，哪些需要 Judge？

原50頁；圖內編號50

重點、講稿與轉場
  • 可明確判定的規則用程式；需要理解語意的摘要或證據支持程度，用 Judge 或人工輔助。
  • Judge 也會出錯，不是保證器。

到這裡我們知道要檢查結果、路徑和工具使用。接著是方法：能明確判定的規則用程式，摘要或證據支持程度需要理解內容，再由 Judge 或人工輔助。Judge 不是保證器。

接下一頁：檢查方法確定後，還要持續累積測試情境。

43｜踩過的坑，留進回歸測試

原51頁；圖內編號51

重點、講稿與轉場
  • 測試集從需求與 SOP 起步，持續加入真實失敗和邊界情境。
  • 昨天踩過的坑要留在回歸測試，讓後續修改能自動檢查。

回歸測試就是修改後重查原本的能力。第一版情境可從需求與 SOP 拆出來；遇到真實失敗就補進去，也可讓 AI 找未測分支。昨天踩過的坑，明天應該能自動檢查。

接下一頁：同一個案例測過一次，就能認為穩定嗎？

44｜同一個案例，要重跑看穩定性

原52頁；圖內編號52

重點、講稿與轉場
  • 同一 Scenario 重跑，觀察不同 Run 的穩定性。
  • 通過門檻依風險與成本設定；有限次全過不保證未來永遠成功。

同一情境也可能每次走得不同，所以要重跑觀察。主稿用十次九次、五次全過說明門檻選擇。有限次通過不保證未來永遠成功；要依風險和可負擔成本訂標準。

接下一頁：而且原本失敗的案例穩了，還不代表這次修改就可以接受。

45｜修好這次，其他情境有沒有退步？

原53頁；圖內編號53

重點、講稿與轉場
  • 修好一個失敗，其他原本通過的場景可能退步，要重跑回歸。
  • 既然能驗證修改是否有效，就可以考慮讓 AI 協助寫與改 Skill。

修好漏步驟不代表新版 Skill 整體更好。其他情境可能因同一句修改而退步，因此要重跑回歸。既然我們能驗證修改是否值得接受，撰寫與修改 Skill 還需要全部由人手工完成嗎？

接下一頁：有了驗證標準，就可以讓 AI 產生 Skill，再用測試判斷差距。

46｜Skill 交給 AI 寫，再用 Evaluation 驗證

原54頁；圖內編號54

重點、講稿與轉場
  • 讓開發用 AI 讀 PRD、SOP 與程式碼，產生第一版 Skill。
  • 用 Evaluation 找出實際行為與目標的差距；這個 AI 不是正式執行任務的 Agent。

前面建立了驗證結果、路徑和工具使用的方法。於是 Skill 不必由人逐句雕琢。我讓開發用 AI 讀 PRD、SOP 和程式碼產生第一版，再跑 Evaluation 找出和預期的差距。這裡的 AI 是協助開發的角色，不是正式任務的 Agent。

接下一頁：測試沒有符合預期時，把執行紀錄交給 AI 分析並修改。

47｜把失敗紀錄交給 AI，修完再跑回歸

原55頁；圖內編號55

重點、講稿與轉場
  • Evaluation 指出差距，Log 與 Trace 提供材料，讓 AI 分析並修改 Skill。
  • 修完再跑回歸，符合接受條件才送審；不是無限盲目重試或只追分數。

Evaluation 指出實際行為與目標的差距，Log 和 Trace 提供追查材料。AI 據此提出 Skill 修改，再跑回歸。尚未符合就繼續修正；符合接受條件再送審。這不是用分數證明完美，也不是讓 AI 無限盲目重試。

接下一頁：人不再逐句撰寫，但仍然要定義成功與接受標準。

48｜人定義成功標準，修改用測試結果驗收

原56頁；圖內編號56

重點、講稿與轉場
  • 人定義成功標準、要測的場景與不可接受的風險；AI 產生候選修改。
  • 不能為過關放寬標準，驗收要看修改差異、測試結果與對應紀錄。

人的重心轉為定義什麼算成功、該測哪些情境與哪些風險不能接受。AI 可以產生與修改 Skill，但不能為了過關任意放寬標準。接受候選修改時，要看修改差異、測試結果和對應紀錄。

接下一頁：這個循環會反覆進行，因此成本也要一起被觀察。

49｜每輪產生、測試與修正，都要留下成本紀錄

原57頁；圖內編號57

重點、講稿與轉場
  • 成本包含 AI 讀紀錄、改 Skill、測試與回歸，也包含正式執行。
  • 每輪記錄 Tokens、工具次數、重試與延遲，才能比較效果與代價。

這個循環不是免費的。AI 讀紀錄和修 Skill、測試和回歸都需要資源。重點不是先問付不付得起，而是記錄每輪 Tokens、工具次數、重試和延遲，知道成本在哪裡，才能比較修改的效果與代價。

接下一頁：不能每次遇到問題，就只靠更大的模型與更多重試。

50｜模型會越來越聰明，但是你的口袋沒有越來越深

原58頁；圖內編號58

重點、講稿與轉場
  • 模型會越來越聰明，但是你的口袋沒有越來越深。
  • 改善不能只靠更大模型、更長 Context、更多重試或 Judge，要用紀錄判斷代價。

模型會越來越聰明，但是你的口袋沒有越來越深。不能每次遇到問題就只加大模型、加長Context或增加重試。能觀察、驗證並看見成本，才有依據決定怎麼改進。

接下一頁：回頭看開場的六個問題，這些責任一起組成 Runtime。

51｜六個問題，長成一套 Runtime

原59頁；圖內編號59

重點、講稿與轉場
  • 回扣六個責任：資訊、流程、邊界、追查、驗證與成本。
  • 人的確認與接受標準貫穿其中，依任務風險逐步補成可治理的 Runtime。

給必要資訊、說清流程、守住操作與結論邊界，再追查、驗證和觀察成本。人的確認與企業接受標準貫穿其中。這些責任隨任務風險逐步補上，讓一個循環成為可以治理的 Runtime。

接下一頁：所以回到最初那幾行程式碼，我最後想留下的是這句話。

52｜Tool Loop 讓它跑起來

原60頁；圖內編號60

重點、講稿與轉場
  • Tool Loop 讓它跑起來，Runtime 讓它可以交付。
  • Agent 不只是模型，還需要限制、觀察、驗證與持續改善的執行系統。

Tool Loop 讓它跑起來，Runtime 讓它可以交付。Agent 是模型能力，加上一整套能限制、觀察、驗證並持續改善它的執行系統。這是我自己刻框架後，真正學到的事。
