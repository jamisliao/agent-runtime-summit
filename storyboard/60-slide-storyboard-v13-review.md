### 畫面文字

下一步需要什麼？｜任務要求與規則｜這一步要讀｜這一步用不到｜只需交給工具

### 畫面設計

把09同一批卡片展開：任務要求與規則固定在上方；資料卡依本次用途分成三組，分別標「這一步要讀」「這一步用不到」「只需交給工具」。以模型對話泡泡、暫存資料庫、工具文件三種語意 icon 輔助辨識，不畫成三種永久資料類型。珊瑚色只圈出標題的「下一步」。無根因、幻覺、結論或因果線索。

### 搭配講稿

重新看這些內容，我發現有些結果前面已經用過，這一步暫時用不到；有些欄位和現在的操作無關；還有一整包資料，只是準備交給下一個工具處理。任務要求和適用規則仍要帶著，但工具曾經回過的內容，不必每一輪都原封不動地交給模型。判斷的依據，是現在要做的下一步。

### 畫面文字

依下一步需要｜本輪 Context｜任務要求與規則｜必要內容｜目前狀態｜系統儲存｜完整資料｜需要時再取

### 畫面設計

承接10展開的資料，右側 Context 只呈現任務與規則、必要內容、目前狀態三張清楚的卡；左下用資料庫圓柱保存完整資料。從資料庫到 Context 的單向虛線標「需要時再取」，使未進本輪 Context 的內容仍有去處。選取關係以「依下一步需要」標示，不畫刪除、垃圾桶或固定必做處理流水線。底線：先決定。

### 搭配講稿

## Slide 13｜分析 Log，先挑出這次需要的內容

### 畫面文字

## Slide 15｜Data Ref 讓工具取回完整資料

段落：① 資訊

### 核心訊息

資料搬運與模型選動作分工，完整資料保留在系統。

### 畫面文字

流程示意｜系統資料｜Tool A｜完整資料｜系統儲存｜模型控制｜status＋data_ref｜LLM 選下一步｜Tool B｜依 Ref 取資料

### 畫面設計

採使用者偏好的上下兩條線：上方 Tool A 將完整資料送入系統儲存；下方 status＋data_ref 交給 LLM，再傳給 Tool B。Tool B 用虛線指向儲存表示取件請求，儲存用實線回到 Tool B 表示資料回傳。主標籤在節點附近，不把必要解釋放底部。底線：無。

### 搭配講稿

模型傳 Ref，工具在服務端解析並取回資料。大腦看燈號，管線傳重貨。這也讓資料使用受允許的操作限制；Ref 是否可讀、能做什麼，仍由系統檢查。

## Slide 16｜Context 越重，越吃模型能力

段落：① 資訊

### 核心訊息

Context 裡的資料、規則與流程狀態越多，模型要維持工作流的難度越高；原本能完成任務的輕量模型，也可能開始漏步驟或提早停止。

### 畫面文字

Context 負載｜資料｜規則｜工具結果｜流程狀態｜模型能力｜守住步驟｜漏步驟｜提早停止

### 畫面設計

畫面由左到右呈現同一條因果鏈：Context 容器逐漸加入資料、規則、工具結果與流程狀態；中間的模型對話泡泡承接這些內容；右側是一條需要守住的工作流。Context 較輕時路徑完整，較重時其中一個必要節點以珊瑚色虛線表示可能漏掉。不要把重點畫成「碰到容量上限」，也不畫虛構門檻；視覺焦點放在「同一個模型必須同時處理更多東西」。沿用使用者指定的語意 icon，以鋼筆線條與少量排線呈現，保留底部安全留白。底線：越吃模型能力。

### 搭配講稿

Context 裡放得越多，模型就要同時顧到越多資料、規則、工具結果與流程狀態。問題不只是 Token 有沒有超過上限，而是這個模型還能不能在這個負載下守住整套 Workflow。原本能完成任務的輕量模型，Context 變重後可能開始漏看規則、跳過步驟或提早停止。

## Slide 17｜30k Context，迫使我換成更大的模型

段落：① 資訊

### 核心訊息

同一個 Workflow 在 Context 變重後，26B-A4B MoE 的完成率下降；換成 31B Dense 才恢復。這組觀察呈現的是 Context 負載如何推高模型需求，不是模型排行榜。

### 畫面文字

```text
同一 Skill、測資、Tool、temperature｜每組 10 次
成功次數
26B-A4B MoE・10k：9
26B-A4B MoE・30k：4
31B Dense・30k：9
仍是同一個 Workflow
有限樣本，非通用排名
```

### 畫面設計

正式直條圖：X 軸為三組模型與 Context 條件，Y 軸為十次執行中的成功次數，刻度用 0、5、10。柱頂標 9、4、9。前兩柱以同色表示同一個 26B-A4B MoE，其中 30k 的柱用珊瑚色框出下降；第三柱以較深色表示換成 31B Dense 後恢復。用一條清楚的閱讀路徑串起「Context 增加」與「換重模型」，旁邊以三個小型缺漏 icon 標出跳過 summary builder、漏 warning、提早停止。樣本限制放在圖旁的可讀位置，不放成底部小字。底線：被迫換重模型。

### 搭配講稿

在同一 Skill、測資、Tool 與 temperature 下，gemma-4-26b-a4b-it-mlx 在 10k Context 成功九次，增加到 30k 後只成功四次；同樣是 30k，換成 gemma-4-31b-it 後又成功九次。失敗時會跳過 summary builder、漏掉 warning 或提早停止。這不是要證明 31B 永遠比較好，而是說明：Context 沒有控制好，原本較輕的模型可能撐不住同一套 Workflow，最後只能用更重的模型補足。這是每組十次的有限觀察，不作通用排名，也不把所有失敗都歸因於長度。

### 接下一頁

但升級模型不是唯一解法。若 Runtime 先把 Working Context 控制好，還需要一開始就付出更重模型的成本嗎？

## Slide 18｜Context 管理會影響需要多大的模型

段落：① 資訊

### 核心訊息

Context 負載會影響完成 Workflow 所需的模型能力。遇到長 Context 失敗時，先整理 Working Context 並重跑，再判斷是否真的需要升級模型。

### 畫面文字

整包放入｜Context 變重｜可能需要更重模型｜較高推論負擔｜依下一步需要｜Working Context｜原模型重新驗證｜再決定是否升級

### 畫面設計

左右兩條清楚的決策路徑。上方路徑：完整資料與工具結果整包進 Context，容器變重，接著指向「可能需要更重模型」與較高推論負擔。下方路徑：完整資料留在 Runtime，summary、control signal 或 data_ref 進入 Working Context，接著回到原模型與同一個 Workflow，標示「重新驗證」。只有重跑仍不足時，箭頭才通往升級模型。兩條路徑共用同一個任務終點，避免讓人誤解成不同難度的任務；也不要畫成整理後 MoE 必然成功。底線：整理後再驗證。

### 搭配講稿

換成 31B Dense 可以把這組測試的完成次數拉回來，但代價通常是更高的推論負擔，而且實際速度仍會受到硬體、量化與推論框架影響。另一個應先驗證的選項是整理 Context：完整資料留在 Runtime，只把這一步需要的內容、狀態與控制訊號交給模型。現有數據沒有直接證明整理後的 26B-A4B 一定能恢復，因此正確做法是用原模型重跑同一個任務；如果已能穩定完成，就不必先升級模型。Context Management 不只是省 Token，也可能降低完成任務所需的模型能力與算力。

### 接下一頁

那麼，整理到什麼程度才算有效？判斷標準不能只是 Token 變少，而是同一個任務仍能穩定完成。

## Slide 19｜Working Context 不是越短越好

段落：① 資訊

### 核心訊息

好的 Working Context 要同時做到兩件事：保留完成下一步需要的資訊，並讓指定模型能穩定完成同一個任務。

### 畫面文字

完成下一步所需｜任務要求｜適用規則｜必要資料｜目前狀態｜不相關原文留在 Runtime｜指定模型｜同一任務｜穩定完成

### 畫面設計

中央放一個清楚的 Working Context 容器，只保留任務要求、適用規則、必要資料與目前狀態；不相關原文以資料文件留在旁邊的 Runtime 儲存。右側不是 Token 計量表，而是指定模型走完同一條 Workflow。用兩個大型驗收記號標示「資訊足夠」與「任務完成」，不要把目標畫成越短越好，也不使用虛構的最佳 Token 數。底線：資訊足夠，任務完成。

### 搭配講稿

Context Management 的目標不是把內容刪到最少，而是留下完成下一步需要的資訊，同時移除不必交給模型的負擔。最後仍要看指定模型能不能在同一個任務裡守住規則並完成 Workflow。Token 變少只是手段，任務能穩定完成才是驗收標準。

### 接下一頁

要確認整理前後是否真的改善，就要用同一個任務重跑，並留下每次 Run 的條件與結果。

## Slide 20｜怎麼證明整理 Context 有幫助？

段落：① 資訊

### 核心訊息

固定任務條件並重跑，才能比較 Context 整理是否讓原模型恢復穩定，或是否仍需要升級模型。

### 畫面文字

同一個任務｜固定 Skill、測資、Tool、temperature｜Run A｜Run B｜模型｜Context tokens｜完成結果｜失敗型態｜一次改一個條件

### 畫面設計

畫面以兩次並排的 Run 為主，不畫成抽象欄位清單。上方共用一條固定條件帶：同一 Skill、測資、Tool 與 temperature。Run A 與 Run B 各自列出模型、Context tokens、完成結果與失敗型態；只把這次刻意改變的條件用珊瑚色框出。若沒有整理後的實測值，就使用欄位模板或「待重跑」標籤，不捏造結果。底線：一次改一個條件。

### 搭配講稿

只說模型怪怪的，無法判斷 Context 整理有沒有幫助。要固定 Skill、測資、Tool 與 temperature，用同一個任務重跑，並把模型、Context tokens、完成結果與失敗型態放在同一次 Run 裡。一次只改一個條件，才知道改善來自 Context 整理、模型升級，還是其他變動。Token 同時是成本紀錄與工作負載線索，後面談成本時會再回來。

### 接下一頁

即使驗證後確認資訊已經足夠，Context Management 仍只能決定模型看到什麼；它不能保證必要步驟一定被執行。

## Slide 21｜資訊給對了，流程仍可能走錯

段落：① 資訊

### 核心訊息

收束 Context 段落並延續同一個 Log 案例：資料準備正確，只代表模型能開始分析；任務是否完成，還要看正式交付流程有沒有走完。

### 畫面文字

Working Context｜相關 Log｜必要規則｜分析差異｜正式報告尚未交付｜資訊準備完成｜任務仍未完成

### 畫面設計

延續前面 Log 的語意 icon。左側是已整理好的 Working Context，包含相關 Log、任務要求與目前狀態；中間是「分析差異」節點；右側保留一份尚未完成的正式報告輪廓，標示「交付尚未完成」。不要在這頁提前介紹 Builder，也不重畫篩選、Ref 或模型比較。主視覺讓聽眾看見「資訊準備完成」與「任務完成」之間仍有距離。底線：任務仍未完成。

### 搭配講稿

到這裡，Context Management 已經把這次分析需要的 Log、規則與狀態準備好，模型也能開始分析差異。但這個任務的終點不是一段分析文字，而是一份正式報告。報告必須包含指定的分類、warning、統計與明細。資訊準備完成，只代表模型看得到需要的材料；交付流程還沒有完成。

### 接下一頁

既然任務還有一段正式交付流程，下一個問題就是：流程寫進 Skill 之後，模型是否每次都會照著完成？

## Slide 22｜流程寫進 Skill，模型真的會照做嗎？

段落入口：② 用 Evaluation 看見流程偏離

### 核心訊息

Skill 能把 SOP 說清楚，但一次成功的示範不足以證明模型會穩定照流程完成任務。

### 畫面文字

Skill 裡的 SOP｜步驟 1｜步驟 2｜必要 Operation｜退出條件｜模型每次都會照做嗎？

### 畫面設計

入口版式採單一主構圖。左側是一張寫有清楚步驟的 Skill 文件，右側是一條尚未走完的手繪執行路徑，中央用一個大問號連接兩者。不要在這頁放 Builder、Guard 或失敗類型；讓視線只落在「寫下流程」與「實際執行」之間的落差。主標與問句維持大字，重要文字不得靠近底部分享介面。底線：每次都會照做嗎？

### 搭配講稿

Context 準備好之後，模型已經看得到相關 Log、任務規則與目前狀態。接下來的問題是，它會不會照 Skill 把流程完成。我一開始以為，只要把第一步、第二步、停止條件與輸出格式寫清楚，模型就會照著走。但一次執行成功，只能證明這一次有成功，還不能證明流程穩定。

### 接下一頁

要看見這種不穩定，不能只挑一個成功案例，而要固定條件反覆執行同一個任務。

## Slide 23｜同一個任務，多跑幾次才看得出問題

段落：② 流程 Evaluation

### 核心訊息

固定測試條件並重複執行同一個 Scenario，才能觀察模型是否穩定完成指定流程。

### 畫面文字

同一個 Scenario｜同一版 Skill｜同一組測資｜同一個 Tool｜同一個模型設定｜重複執行 10 次

### 畫面設計

中央放一份 Scenario 測試文件，向右展開十條等距的手繪執行線，像同一個起跑點重跑十次。固定條件只放在起點周圍，以四個清楚的 icon 表示 Skill、測資、Tool 與模型設定，不做成小卡片矩陣。十條線的終點先保持模糊，下一頁再揭示差異。畫面留白充足，文字維持簡短且大於簡報最低可讀尺寸。底線：重複執行。

### 搭配講稿

我用 LLM Evaluation 固定同一版 Skill、同一組測資、同一個 Tool 與同一組模型設定，再讓同一個 Scenario 重跑多次。這樣才能排除案例不同造成的干擾，觀察模型在相同條件下，是否每次都走完相同的必要步驟。

### 接下一頁

當同一個任務重跑多次，問題才真正浮現：答案都有產生，執行過程卻不一致。

## Slide 24｜答案都有產生，執行路徑卻不一樣

段落：② 流程 Evaluation

### 核心訊息

Final Answer 的存在會掩蓋流程偏離；Evaluation 必須比較實際執行路徑，而不只比較最後文字。

### 畫面文字

正常完成｜跳過必要 Operation｜順序錯誤｜提早停止｜繞過 fallback｜每次都有 Final Answer

### 畫面設計

沿用23的十條執行線，這一頁把其中幾條攤開成不同路徑。正常路徑完整抵達終點；其餘路徑分別用缺口、交換節點、提前終止與繞路表示失敗類型。所有路徑右側都有同樣的 Final Answer 文件 icon，形成「看起來都有答案」的視覺反差。不要用密集表格，也不要將錯誤塞進小字註解。底線：路徑卻不一樣。

### 搭配講稿

重跑後我看到的不是單純答對或答錯。有些 Run 正常完成，有些跳過必要 Operation，有些順序錯誤、提早停止，或者繞過 fallback。麻煩的是，它們最後常常都會產生一段看起來合理的 Final Answer。如果 Evaluation 只看最後文字，就會把流程錯誤當成成功。

### 接下一頁

其中一個最典型的失敗，是模型跳過固定的 Summary Builder，自己交出摘要。

## Slide 25｜其中一次：模型跳過 Builder，自己交摘要

段落：② 流程 Evaluation

### 核心訊息

Skill 明確要求呼叫 Builder，模型仍可能跨過必要 Operation，直接產生看似完成的輸出。

### 畫面文字

預期路徑｜analyze_discrepancies｜build_execution_summary｜正式報告｜實際路徑｜LLM 自行摘要｜Builder 未呼叫

### 畫面設計

使用上下兩條大型路徑，不做左右卡片。上方以藍綠色呈現預期路徑，三個節點依序為分析、Builder 工具文件、正式報告。下方以珊瑚色呈現實際路徑，從分析節點跨過中央 Builder 的位置，直接落到「LLM 自行摘要」。被跳過的 Builder 保留清楚輪廓並加上斜線，讓觀眾一眼看見缺少哪一步。底線：Builder 未呼叫。

### 搭配講稿

這個案例的 Skill 已經寫明，分析差異後要呼叫 `build_execution_summary`。但某些 Run 會跳過 Builder，由模型自己組一段 Final Summary。它沒有發生 exception，畫面上也確實出現了一段答案；只有把實際路徑與預期路徑並排，才看得出必要 Operation 根本沒有執行。

### 接下一頁

跳過 Builder 為什麼不是一個小小的實作差異？因為兩種路徑交付的東西並不相同。

## Slide 26｜看起來完成，實際少了必要交付

段落：② 流程 Evaluation

### 核心訊息

Builder 被跳過後，Final Answer 雖然有內容，固定格式與必要資訊卻可能缺失。

### 畫面文字

正式報告｜固定格式｜完整分類｜必要 warning｜統計與明細｜LLM 自行摘要｜格式不符｜分類漏掉｜必要內容缺失

### 畫面設計

主畫面是一份正式報告被一條垂直線分成「Builder 輸出」與「LLM 自行摘要」兩半。左半欄位完整、結構整齊；右半保留相同欄位位置，但用珊瑚色空白與斷線標出缺漏。不要填虛構業務內容，也不要用勾叉清單取代主圖。視覺焦點放在同一份交付規格中哪些部分消失。底線：Final Answer 不等於完成交付。

### 搭配講稿

Builder 會收斂固定格式、完整分類、必要 warning、統計與明細。模型自行生成的摘要可能讀起來通順，卻出現格式不符或分類遺漏。對這個任務來說，有一段文字不代表交付完成。這也是為什麼「Final Answer 看起來有內容，不代表 Workflow 正確完成」。

### 接下一頁

因此 Evaluation 不能只評摘要寫得像不像，還要驗證流程中該發生的事情是否真的發生。

## Slide 27｜Evaluation 不只評答案，也要評執行過程

段落：② 流程 Evaluation

### 核心訊息

Agent Evaluation 必須同時驗證最終輸出與關鍵執行事件，才能辨識看似成功的流程失敗。

### 畫面文字

Final Output｜必要 Operation 是否發生｜順序是否正確｜是否提早停止｜是否使用指定 Builder｜退出條件是否成立

### 畫面設計

中央是一條帶時間刻度的 Trace，必要 Operation 以少量大型節點表示。上方放最終輸出文件；下方用放大鏡圈出 Builder、停止點與順序，不使用六張獨立檢查卡。讓「答案」與「過程」同時落在同一條執行紀錄上。重點詞可用藍色與珊瑚色手繪圈線強調，但避免每個詞都著色。底線：也要評執行過程。

### 搭配講稿

對 Agent 來說，Evaluation 不只比較 Final Answer。它還要確認必要 Operation 是否發生、順序是否正確、模型有沒有提早停止，以及退出條件是否成立。這些證據來自 Trace 與 Runtime Event。這樣才能把「答案不好」和「流程根本沒有走完」分開。

### 接下一頁

有了 Final Output 與 Trace，Evaluation 就能衡量模型有多常按照 Skill 的說明完成流程。

## Slide 28｜十次執行，有幾次真的照 Skill 走完？

段落：② 流程 Evaluation

### 核心訊息

Skill 以自然語言說明下一步該做什麼；Evaluation 比對 Skill 要求、實際 Trace 與最終輸出，估計模型遵守流程的穩定度。

### 畫面文字

Skill 自然語言說明｜預期步驟｜實際 Trace｜重複 Scenario｜通過 Run ÷ 全部 Run｜遵守流程的機率

### 畫面設計

左側是一份以自然語言寫成的 Skill 文件，圈出「分析後呼叫 Builder」與「取得正式報告後才結束」兩句規則。中央展開多次相同 Scenario 的 Trace，有些完整經過 Builder，有些跨過或提前停止。右側用一個簡單的大比例尺呈現「通過 Run ÷ 全部 Run」，不畫成產品儀表板，也不加入 State Machine、YAML 或 Runtime 強制閘門。底線：有多常照 Skill 執行。

### 搭配講稿

我的流程規則仍然以自然語言寫在 Skill 裡，LLM 讀完後，依當下情況判斷下一步。Trace 記錄它實際呼叫哪些 Operation、是否跳步，以及何時停止。Evaluation 再用多個 Scenario 與重複 Run，比對模型有沒有按照 Skill 的說明做判斷與執行。它讓我知道在目前的測試範圍內，模型遵守流程的比例有多高。

### 接下一頁

這個比例可以很高，甚至測試案例全部通過；但它仍然是一份測試結果，不是未來每一次執行的保證。

## Slide 29｜Evaluation 100%，仍然不是零風險

段落：② 流程 Evaluation

### 核心訊息

Evaluation 能驗證模型在已覆蓋 Scenario 中的遵守率，卻無法消除機率模型在未來執行中偏離 Skill 的可能性。

### 畫面文字

已測 Scenario｜Evaluation：100% Pass｜未來輸入與不同 Context｜LLM 仍可能偏離｜測試通過率不是執行保證

### 畫面設計

左側是一個清楚圈起的 Evaluation 測試範圍，範圍內多個 Scenario 全部為綠色，中央大字寫「100% Pass」。右側是測試範圍之外的一次未來執行，新的輸入、不同 Context 與模型判斷匯入同一條路徑，其中保留一條細小但清楚的偏離分支。不要使用骰子或誇張故障圖示，以免把機率模型畫成純隨機。底線：100% 是測試結果，不是零風險。

### 搭配講稿

Evaluation 做得越完整，我們越能知道模型在大部分場景中有多高的機率按照 Skill 執行，也能透過失敗案例持續修改 Skill、模型或 Context，降低觀察到的錯誤率。但 Skill 始終是自然語言說明，LLM 也始終是機率模型。即使 Evaluation 在目前案例中得到 100%，未來某次執行仍然可能不準，或者沒有按照 Skill 的說明做判斷。

### 接下一頁

因此下一個設計問題不是「Evaluation 還能不能再多做一點」，而是「這種錯誤偶爾發生一次，我能不能接受」。

## Slide 30｜錯誤能不能放行？

段落入口：③ 守住不能接受的錯

### 核心訊息

### 畫面設計

入口版式用一條垂直分界線形成兩個寬鬆區域，不做成卡片。左側是 Skill 文件、Evaluation 放大鏡與可重試箭頭，標示「可以接受偶發錯誤」；右側是實際閘門與人工確認 icon，標示「一次都不能接受」。中央只放一個大問題「錯誤可以通過嗎？」。底線：可容錯用 Skill，不可容錯用 Guardrail。

### 搭配講稿

## Slide 31｜把不可接受的錯，變成可檢查的條件

段落：③ Guardrail

### 核心訊息

### 畫面文字

### 畫面設計

## Slide 32｜LLM 可以提出，不能自己放行

段落：③ Guardrail

### 核心訊息

LLM 產生的 Tool Call、Claim 與操作都只是候選提案；系統完成相應檢查後，才允許它變成正式輸出或實際影響。

### 畫面文字

LLM 提出｜Tool Call｜Claim｜高風險操作｜系統檢查｜格式與業務規則｜Evidence｜Authorization｜符合才執行或輸出

### 畫面設計

左側是一個 LLM 對話泡泡，提出三個大型語意物件：Tool Call 文件、Claim 對話卡與高風險操作提案。三者走向中央同一道系統邊界，但在邊界上分別標示「格式／業務規則」「Evidence」「Authorization」。右側才是 Tool 執行、正式回答與實際寫入；未通過的提案停在邊界前。不要畫四座連續閘門，也不在這頁提前展開人工 Approval。底線：最終放行權不在 LLM。

### 搭配講稿

Skill 告訴 LLM 應該怎麼做；Guardrail 改變的是最後的決定權。LLM 可以提出 Tool Call、形成 Claim，或者建議一個操作，但不能自己宣告它們已經安全。Tool Call 要先符合格式與業務規則，Claim 要有 Evidence 支持，實際操作則要通過 Authorization 與當下條件。只有檢查通過，提案才會成為正式輸出或產生實際影響。

### 接下一頁

回到前面分析 Log 的案例。當時我們處理的是要給模型哪些資料；現在看模型讀完後提出的根因結論，是否有足夠證據支持。

## Slide 34｜證據不足，就不能說成確定結論

段落：③ Guardrail

### 核心訊息

Evidence Boundary 要求模型區分已觀察事實、待驗證假設與證據不足，避免把推測包裝成確定原因。

### 畫面文字

已觀察事實｜待驗證假設｜證據不足｜缺少哪些證據？｜不能升格為確定結論

### 畫面設計

將一個 Claim 文件放在中央，往右只有三個清楚的大型出口：事實、假設、證據不足。確定結論的出口前放一道 Evidence 閘門；Evidence 不足時，路徑轉向假設或缺口說明。不要畫成真假二選一，也不要使用評分儀表板。用珊瑚色手繪底線只強調「不能升格」。底線：不能升格為確定結論。

### 搭配講稿

時間接近可以成為調查線索，但還不能證明因果。若目前資料只能支持可能性，就把它保留為待驗證假設；若證據不足，就清楚說明還缺什麼。Evidence Boundary 要阻止的不是所有推論，而是沒有足夠支持卻被包裝成確定結論的輸出。

### 接下一頁

系統可以檢查規則與證據，但任務是不是使用者真正要的、某次操作是否允許，有些情況需要把決定交回給人。這不是讓人把證據不足的推測批准成事實。

### 搭配講稿

## Slide 36｜執行前，讓使用者確認 Agent 理解的目標與範圍

段落：③ HITL

### 核心訊息

當指令同時包含目標、範圍與排除條件，Agent 先整理自己的理解，再由使用者確認後開始執行。

### 畫面文字

使用者：找 A 類、排除 B，只處理最近三天失敗項目｜Agent 的理解｜目標：A｜排除：B｜範圍：最近三天｜狀態：失敗｜這是你要的嗎？｜確認／修改／退回

### 畫面設計

由左到右形成一條清楚的理解流程。左側用大型對話泡泡完整放入一句簡短使用者指令；中央是 Agent 整理出的目標、排除、範圍與狀態；右側只放大問題「這是你要的嗎？」以及確認、修改、退回三個動作。不要畫成設定表單或使用大量小字。底線：確認理解後再執行。

### 搭配講稿

像「找 A 類、排除 B，而且只處理最近三天失敗項目」，同時包含目標、排除條件、時間範圍與狀態。Agent 先把自己理解的內容整理出來，讓使用者確認、修改或退回，再依確認後的版本開始呼叫工具。這裡確認的不是「允不允許操作」，而是「Agent 有沒有理解正確」。

### 接下一頁

## Slide 37｜一開始理解錯，後面全部成功也沒有用

段落：③ HITL

### 核心訊息

### 畫面文字

### 畫面設計

## Slide 39｜批准後，執行前仍要重新檢查條件
