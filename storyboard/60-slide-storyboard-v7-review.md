## Slide 03｜會動！也確實只需要幾行程式碼

### 核心訊息

最小實作可以啟動 Agent，但還沒有處理後面的責任。

### 畫面文字

```text
while not done:
  response = call_llm(messages)
  if response.tool_call:
    result = execute(response.tool_call)
    messages.append(result)
  else:
    return response.final_answer
```

### 畫面設計

單一大型程式碼區，強調 call／execute／append；不加入未解釋的模組。

### 搭配講稿

這是概念示意，先省略 API 格式與細節。基本 Loop 很快就能動，也真的可以完成簡單任務。

## Slide 10｜Log 沒有說的，模型自己補上了

### 核心訊息

資料片段可以是真的，模型補上的因果卻未經證實。

### 畫面文字

資料裡有：時間、Error、Service／模型補上：所以 A 導致 B

### 畫面設計

左側為幾筆 Log 片段；右側結論中，來自資料的字是深藍，額外補出的因果是珊瑚紅虛線。直接標「未被證實」，不用機器人或抽象警報。

### 搭配講稿

模型確實讀到了 Error，但它把局部 Service Error 說成整個系統的 Root Cause。問題不是完全沒資料，而是回答裡多出了資料沒有證明的部分。畫面內容為示意，不當作實際原始 Log。

## Slide 11｜時間接近，不代表存在因果

### 核心訊息

辨識把共同出現或時間相近推成因果的跳躍。

### 畫面文字

先後發生 ≠ 因果成立／缺少的連結，不能直接補成原因

### 畫面設計

上方以時間軸呈現兩個觀察事件；下方紅色因果箭頭中段留缺口，標「缺少證據」。兩種關係視覺上明確區分。

### 搭配講稿

幾筆 Log 都可能是真的，發生時間也很近，但中間還缺少足以建立因果的資訊。模型卻可能用合理的故事補完，把可能性說成確定原因。

## Slide 14｜Data Ref 讓 Tool 按需取回完整資料

### 核心訊息

完整 Payload 留在系統，LLM 傳遞控制資訊，Tool 解析 Ref。

### 畫面文字

SYSTEM DATA／LLM CONTROL／status + data_ref／Tool B(input: data_ref)

### 畫面設計

沿用使用者認可的雙層 Data Ref 構圖：Tool A→System State，Ref→LLM→Tool B，Tool B 向上解析 Ref。認可圖是視覺基準；核對候選檔案後選定，不以檔名推定已核准。

### 搭配講稿

Tool A 產生資料後，完整內容留在 Runtime State 或儲存層。模型看到 status 和 data_ref，選擇下一個 Operation；Tool B 在 Server Side Resolve。分析需要內容時仍可提供必要片段，這不是全面禁止模型看資料。

## Slide 33｜證據不足，就保留不確定性

日期範圍傳錯、漏 Ref、前置條件不足、把 Tool Error 當正常資料，都是需要明確驗證的行為。

## Slide 49｜能確定的規則，就不要再猜

## Slide 50｜踩過的坑，留進 Regression

## Slide 52｜Eval 要指出下一步怎麼修

## Slide 53｜Agent 成本，來自整條執行鏈

## Slide 57｜讓 Skill 在驗證中持續改進

### 搭配講稿
