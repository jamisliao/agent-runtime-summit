# Agent Runtime｜58頁講述重點

依v39分頁稿整理，對應v39圖片。每頁保留來源主旨、2–3個講述重點及轉場，這是講者提示，不取代原講稿。

## 01｜自己刻 Agent 框架，最難的不是呼叫 LLM

主旨：用親身失敗與修正經驗，說明從 Tool Loop 到可交付 Runtime 的過程。

- Tool Loop 能讓模型呼叫工具，但還不足以承接真實任務。
- 今天沿著實作遇到的問題，說明如何走到可交付的 Runtime。

接下一頁：先看我一開始以為的 Agent 長什麼樣。

## 02｜這個 Tool Loop，幾行程式碼就能跑起來

主旨：LLM 選動作、Tool 執行、結果交回 Context，形成最小可運作循環；能跑起來仍不是可交付。

- 模型要求工具時才執行；結果交回 Context，繼續問模型。
- 最小循環確實能跑，但還沒承接真實任務的責任。

接下一頁：直到它開始碰到真實任務：工具會動、模型會答，就代表可以交付嗎？

## 03｜你以為這樣就結束了嗎？

主旨：從 Demo 成功，轉入真實任務帶來的責任。

- 工具會動、模型會回答，只是 Demo 成功。
- 企業任務可能沒有 exception，卻仍交出錯誤結果。

接下一頁：這些問題，慢慢長成六項必須承接的責任。

## 04｜會動之後，六個問題攤開了

主旨：建立全場問題地圖，讓結尾能逐一回扣。

- 六個問題：給什麼資訊、怎麼完成流程、哪些錯不能放行。
- 出錯如何追查、修改如何驗證、每次執行與測試的成本在哪裡。
- 這是全場的問題地圖，最後會回扣整套 Runtime。

接下一頁：在展開之前，先交代我為什麼選擇自己刻。

## 05｜為什麼選擇自己刻？

主旨：自己刻的動機，是掌握模型選擇、執行可控性與既有企業治理的整合。

- 自己刻的理由：模型選擇、執行可控，以及既有企業治理整合。
- 這場聚焦單次任務的執行與驗證，不展開模型介接及跨Session記憶。

接下一頁：所以我決定自己把這個 Runtime 接起來。最初就是前面那個循環：模型選工具、工具執行、結果交回模型。接著，第一個需要我做決定的地方出現了：工具回來的這一大包資料，該怎麼交回去？

## 06｜第一個問題：工具結果，怎麼交回模型？

主旨：接回開場的 Tool Loop，指出「工具結果交回模型」是第一個要處理的決定，帶入 Context 的用途。

- 回到 Tool Loop：工具已經執行完，結果要怎麼交回模型？
- Context 是這一輪給模型看的內容，包含使用者要求、規則與工具資料。

接下一頁：當時我的做法很直覺：工具回什麼，我就全部加進去。下一頁就是我最初的接法。

## 07｜每輪都 append，Context 越堆越多

主旨：從每輪累積工具結果，帶出下一步究竟需要哪些資訊，以及完整資料與模型Context應分開處理。

- 每輪整包append，使舊結果、新結果持續累積。
- 先問下一步由誰使用資料：模型分析，或另一個工具處理？
- 工具需要保留完整資料，不等於這一輪模型需要讀完整包。

接下一頁：完整資料仍要保留，但不用全放進模型的Context。下一頁看我怎麼把資料保存與本輪輸入分開。

## 08｜工具結果留完整，給模型的內容按需準備

主旨：工具先回傳完整結果，Runtime保存原始完整資料，供後續工具使用；交給模型的本輪內容則按下一步需要準備。

- 先保存工具的原始完整結果，後續工具仍可取用。
- 給模型的本輪Context按下一步需要準備，不等於把資料全部塞入。

接下一頁：完整結果已經留下來了。如果模型不用讀整包資料，下一個工具怎麼找到它？下一頁看 status 與 data_ref 怎麼分工。

## 09｜模型傳 Ref，工具取完整資料

主旨：模型判斷只需 status 與 data_ref；完整 API 資料由系統保存，下一個工具在服務端依 Ref 取回。

- 模型接收狀態和 Ref，資料搬運由工具與系統處理。
- 取件請求與完整資料回傳分開；Ref 的使用權限仍由系統檢查。
- 只交付下一步需要的資訊，不只是省 Token，也是在減少模型執行負擔。

接下一頁：資料搬運可以只傳 Ref；但如果下一步要模型分析 Log，就得給它相關內容。那該給多少？接下來用分析系統 Log 的案例說明。

## 10｜查線上問題，卻把 Context 塞爆了

主旨：工具查回完整Log不是問題；把大量原始Log原封不動塞回Context，才是這次踩坑的原因。

- 任務是分析線上問題；LLM判斷先查Log，Tool回傳大量原始紀錄。
- 整包原封不動塞回Context，造成Context爆量；取得完整資料不等於模型必須讀完整包。

接下一頁：所以我需要改的，是Log交回模型之前的處理：先依這次線上問題篩選，再放進Context。

## 11｜Log 先篩選，再放進 Context

主旨：依這次線上問題挑選相關Log，再準備給模型的Context；不是把工具查回的完整結果原封不動回塞。

- 先依這次線上問題篩選相關Log，再放進本輪分析用Context。
- 時間範圍、必要欄位、分類片段與摘要按需選用；原始資料保留，需要時再取。

接下一頁：先篩選Log能避免盲目塞爆Context，但控制Context不只是省Token；即使還沒超過上限，也會影響模型同時顧資料與流程的負擔。

## 12｜控制 Context，不只是為了省 Token

主旨：傳 Ref 與按需整理 Log，都是控制模型需要處理的資訊；目的不只是省 Token，也要減少模型同時顧資料與流程的負擔。

- Ref 與資料整理不只是省 Token，也是在減少模型同時處理的負擔。
- 模型還要顧到規則、判斷下一步；Context 沒滿也可能漏步驟。
- 按需提供資訊並保留必要規則；是否有效仍要用同一任務實測，不保證整理後一定成功。

接下一頁：除了內容多少，資訊放在 Context 的哪個位置，也可能影響模型能不能有效利用。

## 13｜資訊放在中間，也容易被 LLM 忽略

主旨：研究在特定任務觀察到位置效應，不能把長視窗當成等量有效利用。

- 關鍵資訊的位置，可能影響模型對它的有效利用。
- 圖表是Lost in the Middle研究的趨勢示意，不是所有模型的通用表現曲線。

接下一頁：這也呼應我的實務經驗：Context 還沒有滿，模型就可能無法正確走完流程。

## 14｜30k Context，迫使我換成更大的模型

主旨：同一個 Workflow 在 Context 變重後，26B-A4B MoE 的完成率下降；換成 31B Dense 才恢復。這組觀察呈現的是 Context 負載如何推高模型需求，不是模型排行榜。

- 同一組測試：26B-A4B MoE 在 10k 成功 9/10，30k 降為 4/10。
- 30k 換成 31B Dense 後成功 9/10，呈現 Context 負載推高模型需求的觀察。
- 每組只有十次，不是通用模型排名，也不能把所有失敗都歸因於長度。

接下一頁：這讓我回頭思考：下一步真的需要模型讀完這麼多內容嗎？不能每次遇到問題，都只用更大的模型補上。

## 15｜Context 管理會影響需要多大的模型

主旨：有效控制Context，是控制完成任務所需模型能力與推論負擔的一個重要設計選擇；不要不加區分地把所有資料交給模型，或只靠升級模型處理問題。

- Context負載會影響完成任務所需的模型能力與推論負擔。
- 先判斷下一步需要什麼；完整資料留在系統，必要資訊和規則交給模型。
- 減少不必要負擔不保證成功，但不應每次都只靠升級模型。

接下一頁：前面我們處理的是，Log要怎麼交給模型。接下來回到任務的交付目標：模型分析完之後，還要交付什麼？

## 16｜分析完 Log，還要交付正式報告

主旨：交代分析結果還需整理成正式報告，指出讓LLM自由撰寫可能造成格式不一致與分類遺漏，帶出下一頁的Builder。

- Log分析完成後，這個任務仍要求交付正式報告。
- 讓LLM自由撰寫，可能產生格式不一致、分類或必要欄位遺漏。
- 報告交付有規格，需要明確安排產生報告的步驟。

接下一頁：在我的案例裡，我準備了專門的Builder，把分析結果整理成固定格式、包含必要內容的正式報告。

## 17｜正式報告，需要由 Builder 產生

主旨：承接第16頁的正式報告需求與自由撰寫風險，說明如何由Builder收斂固定格式、完整分類及必要內容。

- 這個任務要交付固定格式、完整分類、warning、統計與明細。
- 分析結果交給報告Builder，指定格式與必要內容由程式收斂。

接下一頁：工具已經準備好了，我也把分析後要呼叫Builder的要求，寫進Skill。

## 18｜我已在 Skill 寫明：分析後呼叫 Builder

主旨：必要工具與交付步驟已用自然語言寫明。以具體Skill說明建立期待，下一頁立刻對照實際漏Builder的失敗，不再多放一張抽象疑問。

- Skill以自然語言說明分析後呼叫Builder、取回結果再交付。
- 這些是模型收到的指示，不是程式強制執行的狀態機。

接下一頁：但實際執行時，它卻跳過了Builder，直接交出自己寫的摘要。

## 19｜模型卻跳過 Builder，自己寫了摘要

主旨：Skill已寫明分析後呼叫Builder，模型仍跳過它而自行摘要；格式不符與分類漏掉，是必要步驟未完成造成的交付缺失。

- Skill已要求分析後呼叫Builder，但有些Run仍跳過它，自行交出摘要。
- 自行摘要導致格式不符、分類漏掉；指定交付沒有完成。
- 有答案、沒有exception，不等於必要步驟都已執行。

接下一頁：所以不能只看它有沒有回答；有回答，不代表流程正確完成。

## 20｜有回答，不代表流程正確完成。

主旨：從漏Builder及交付缺失，收束成為什麼需要測試：Skill說明要求，不等於模型執行時一定達成；必須實際執行並檢查必要步驟與指定交付。這頁不介紹Trace診斷。

- Skill寫明要求，不等於模型實際執行時一定照做。
- 實際跑任務，檢查必要步驟與指定交付；這就是接下來要介紹測試的原因。

接下一頁：既然有回答不代表流程正確完成，那我們要怎麼知道Agent真的完成了任務？

## 21｜怎麼知道 Agent 真的完成任務？

主旨：先說清楚怎樣才算完成，讓任務有可對照的成功標準。

- 必要操作：確實呼叫Builder。
- 交付成果：交出Builder產生的正式報告。
- 先定義成功標準，才有依據判斷是否完成。

接下一頁：有了明確標準，接著讓模型實際跑一次，再檢查有沒有做到。這就是Evaluation。

## 22｜Evaluation：實際測試 LLM 的表現

主旨：Evaluation的目的，是實際測試LLM在任務中的表現，而不是只相信它的回答或能力描述。

- 用真實執行產生的結果對照任務要求，不只看回答是否流暢。
- 測試可以在受控環境進行；不等於直接操作正式系統。

接下一頁：沿用剛才報告任務的驗收卡，跑完一次後，我們要到哪裡找達標的依據？

## 23｜把實際執行，對回任務要求

主旨：從交付成果確認是否交付，從工具呼叫與回傳紀錄確認Builder操作及交付來源。

- 交付成果：確認指定報告有沒有交出。
- 工具紀錄：確認Builder呼叫與Tool回傳結果。
- 確認交付來源，需要把Tool結果與最後交付對照。

接下一頁：從剛才的核對，可以分成兩個評估面向：最後交付得對不對，以及實際執行的過程有沒有符合要求。

## 24｜Evaluation 要看結果，也要看執行過程

主旨：Outcome Evaluation檢查交付結果是否符合任務要求；Trajectory Evaluation檢查實際執行的訊息與操作，包括必要工具、順序與參數。兩者是評估對象，不是評分者或必須二選一的方案。

- Outcome Evaluation：看最後的交付是否符合要求。
- Trajectory Evaluation：看實際執行的必要步驟、工具與參數。
- 結果與軌跡可一起評估；不是二選一，也不是讀取隱藏思考。

接下一頁：結果與執行過程是評估的面向；接著看判斷方法，可以請模型依準則評審，也可以用程式檢查。

## 25｜這些要求，要怎麼評估？

主旨：Code-based Evaluation與LLM-as-a-Judge是評估方法，均不固定綁定某一對象。Trajectory Matching是程式化比對預期軌跡的一種方式；Judge可評內容，也可評執行軌跡。評估不是執行時Guard，也不保證未來每次正確。

- LLM-as-a-Judge：依評分準則評內容或軌跡，不等同於只看分數。
- Code-based Evaluation：以程式核對明確條件；Trajectory Matching可比對預期步驟。
- 評估對象與方法是兩個維度，能搭配使用；測試通過不等於未來零風險。

接下一頁：以Builder案例來說，呼叫有沒有發生、交付是否對應它的回傳結果，都能做成明確的程式檢查。

## 26｜把明確要求，做成程式檢查

主旨：讓程式核對實際Builder呼叫，以及最後交付是否對應Builder的Tool回傳結果。

- 程式核對實際呼叫紀錄中是否包含指定Builder。
- 對照最後交付與Builder的Tool回傳結果，確認交付是否符合來源要求。
- 每次執行後使用相同標準，記錄各項通過或未通過。

接下一頁：程式檢查訂好之後，下一步是固定條件重跑，看同樣的任務是否穩定達標。

## 27｜固定條件重跑，觀察流程是否穩定

主旨：接續已介紹的Evaluation，說明怎麼觀察穩定度：固定條件、多次執行、按相同標準檢查。與下一頁的未來保證限制分工清楚。

- 固定Skill、測資、Tool與模型設定，重跑同一任務。
- 每次都用相同交付要求檢查必要操作與結果，不以一次成功判定穩定。
- 示意圖不新增成功率；有限觀察不是未來保證。

接下一頁：即使調整到目前這一批測試全部通過，能不能保證下一次也一定照做？

## 28｜測試全過，不代表下次一定照做

主旨：將上一頁的多次測試接到其限制：有限觀察提高信心，卻不保證下次執行。以風險容忍度轉入Guard，而不是跳入新名詞或流程硬鎖。

- 全部通過描述的是目前有限測試，不是未來每次執行的承諾。
- Skill仍是自然語言說明，同案例再執行與新情境都可能偏離。
- 因此要回頭判斷哪些錯可以接受，哪些條件必須由系統守住。

接下一頁：能接受偶發錯誤，就持續用Skill與測試改善；一次都不能接受的條件，就不能只靠模型遵守。

## 29｜不能接受的錯，就不能只靠模型遵守

主旨：用風險容忍度劃分責任：自然語言與測試改善表現，系統承接不可只靠LLM遵守的條件。不是一個Guard就保證所有未知錯誤消失。

- 可接受偶發錯誤的行為，用Skill引導、Evaluation改善。
- 不可接受的條件，需要系統落實檢查與限制。
- 同一個Log報告任務，分開檢查流程遵循與結論依據。

接下一頁：用日期、報告證據和修改權限這三個例子，看看哪些責任要交給系統。

## 30｜把不可接受的錯，變成可檢查的條件

主旨：不可接受的條件需要落到系統：採用工具日期結果、輸出前對照結論證據、修改前由程式檢查權限。Evidence這裡守報告是否新增工具沒有回傳的內容，不改成重新判定工具資料本身真假。

- 日期由確定性工具計算，正式結果採用工具輸出。
- 報告中的結論在正式輸出前，要有對應且相關的工具結果支持。
- 資料修改前由程式檢查權限，權限不足就阻擋修改。

接下一頁：剛才檢查的是「有沒有照流程做」。但流程做了，模型寫出的結論就一定有依據嗎？接著仍用同一個Log報告任務，看工具結果沒有回傳的內容怎麼混進報告。

## 31｜同一份 Log 報告，還可能多出沒有依據的內容

主旨：承接同一個Log報告任務，從流程檢查轉到結論依據：有查回資料，LLM仍可能在報告補出Tool Result沒有的內容。

- 同一個Log報告任務，流程是否照做與結論是否有依據，是兩種檢查。
- 這次守的是輸出結論的工具依據，不是Context選材或重新驗證來源真假。
- 圖中的服務已重啟是教學示意，不是實際報告的逐字引文。

接下一頁：因此不是整份報告附一個引用就好，而是每一項結論，都要逐項對回Tool Result。

## 32｜每一項結論，都要對回 Tool Result

主旨：Evidence是報告結論與相關工具結果之間的支持關係。逐項對照來源與內容，不能只檢查有無Ref欄位，也不能把模型自行生成的敘述當工具證據。

- 每項結論都要有可對應的真實工具結果，而不是LLM自行編造的來源。
- Ref必須有效，對到的結果片段也要和結論相關、內容相符。
- 不是Ref存在就算支持，也不是重新驗證Tool Result本身真假。

接下一頁：找不到對應支持的項目，就不能被當成已有證據的結論，放進正式報告。

## 33｜沒有對應證據的結論，不能進正式報告

主旨：把Evidence要求落到正式輸出：不讓未被工具結果支持的新增結論混進報告。允許說明缺資料，不把缺少證據誤當來源事實已被證偽。

- 有對應且相關Tool Result支持的結論，才進正式報告。
- 工具沒有回傳的內容，不讓LLM自行補成已確認結果。
- 缺資料可以說明限制或補查，不是讓人替無證據結論蓋章。

接下一頁：前面由系統檢查結論是否有證據。接著看人的介入：確認Agent理解的任務是不是我們要的，以及是否允許它執行某項操作。

## 34｜讓人介入：確認理解、批准操作

主旨：Human-in-the-Loop讓人在需要確認的時機介入：確認Agent理解的目標與範圍，或批准它準備執行的操作。

- 確認理解：Agent理解的目標與範圍，是不是使用者要的？
- 批准操作：Agent準備執行的行為，是否允許？

接下一頁：先看任務開始前：讓使用者確認 Agent 理解的目標與範圍。

## 35｜先確認理解，避免做完錯誤的任務

主旨：先讓使用者確認 Agent 理解的目標、排除、範圍與狀態；工具全部成功仍可能執行錯誤任務。

- 執行前先確認目標、排除與範圍，避免後面成功完成錯任務。
- 意圖確認不是操作批准；兩者解決不同問題。

接下一頁：確認理解以外，寫入、扣款或對外通知還需要另一種確認：批准這次操作。

## 36｜寫入、扣款或對外通知，執行前要先批准

主旨：Execution Approval 必須讓人先看懂要做什麼、影響範圍與預覽結果，再決定是否允許執行。

- 寫入、扣款、開單或對外通知，系統要在執行前停下等批准。
- 讓人先看懂提案、影響範圍與預覽，留下批准者、時間和批准版本。

接下一頁：即使人已經批准，真正執行前仍然不能直接沿用舊狀態。

## 37｜批准後，執行前仍要重新檢查條件

主旨：批准與執行之間可能出現狀態變化；Runtime 必須在真正執行前重新檢查前置條件。

- 批准到執行可能相隔一段時間，資料、任務或權限狀態可能已變。
- 執行前重新檢查 Precondition，將批准內容與檢查結果留在 Trace。

接下一頁：前面做了系統檢查與人工確認，但任務仍可能出錯。除了執行前防錯，出了問題也要能回看當時的執行。

## 38｜任務出錯時，要能回看當時的執行

主旨：從執行前的防錯轉向出錯後的追查：把最後發現的問題放回當時的執行過程，尋找需要確認的環節。

- 最終結果顯示問題，回看執行過程才有追查線索。
- 把同一次任務的輸入、回應、工具執行與交付結果對起來。

接下一頁：接著回到前面漏Builder的案例，看看發現問題之後，如何回頭追查當時的執行。

## 39｜發現漏了 Builder，還要查它怎麼發生

主旨：發現漏了Builder只是起點，還要對照當時的實際執行紀錄。

- 缺漏可能在測試或實際使用中發現，不限於Evaluation。
- 最後結果指出問題，當時紀錄才提供追查線索。

接下一頁：要讓這件事可以追查，必須先把這幾類資訊留下來。

## 40｜先留下 AI 能協助追查的資訊

主旨：留下同一次任務的實際輸入、回應、工具呼叫與設定，才能協助追查。

- Context與模型回應：確認實際收到與輸出了什麼。
- Tool呼叫與結果：确认要求、參數、結果或錯誤。
- 版本與設定：保留當時使用的模型及Skill等資訊。

接下一頁：把這些紀錄放回漏Builder的案例，就能逐步對照。

## 41｜漏了 Builder，要對照哪些紀錄？

主旨：用Context、模型回應與Tool執行紀錄，逐段檢查Builder缺在哪裡。

- Context：有送入Builder指示嗎？
- 模型回應：有提出Builder呼叫嗎？
- Tool執行：呼叫有實際執行嗎？

接下一頁：這些紀錄的交叉比對，也可以讓AI幫忙整理。

## 42｜把執行紀錄交給 AI，協助找線索

主旨：讓AI依執行紀錄提出待確認疑點，而不是替缺漏編造原因。

- 把相關執行紀錄交給AI，協助交叉比對。
- 疑點要附紀錄依據；推測仍然需要確認。

接下一頁：找到值得修改的方向之後，還要實際驗證修改是否改善。

## 43｜提出修改，再用 Evaluation 驗證

主旨：追查提供修改方向，Evaluation用實際執行檢查修改效果。

- 先根據追查線索提出候選修改，不預設一定是Skill的錯。
- 修改後重新評估實際流程與結果，不只看文字改得如何。

接下一頁：所以改完Skill，不能只測改動的那一句，而要把整次任務重跑。

## 44｜改完 Skill，整次任務都要重新測

主旨：從Trace提出候選修改，轉入修改驗收；用整次任務的結果、路徑與工具參數判定是否符合既定成功標準。

- 承接追查後的候選修改，這裡開始驗收新版Skill，不重新介紹Evaluation。
- 結果、路徑、工具參數都要檢查，不能只看改動的那句說明。

接下一頁：先看使用者拿到的成果：改完之後，報告符合原本要求了嗎？

## 45｜改完之後，報告符合要求了嗎？

主旨：將Outcome Eval落到新版Skill的報告驗收，不重複一般定義，也不為讓修改通過而放寬既定標準。

- 修改後仍用既定交付要求，檢查格式、分類與必要warning。
- 檢查報告結論是否有對應支持，不以文字流暢代替交付驗收。

接下一頁：報告符合要求了，必要的Builder這次也真的執行了嗎？

## 46｜漏掉的 Builder，這次有呼叫嗎？

主旨：用Trajectory Eval驗收已知漏Builder問題是否仍發生，不再重講看答案不夠的一般概念。

- 驗收這次候選修改，確認本情境要求的Builder確實被呼叫。
- 各情境可以有合法分支，但必要步驟、順序與停止條件仍要符合要求。

接下一頁：即使這次有呼叫Builder，傳給它的Ref和參數也可能不對。

## 47｜呼叫了 Builder，傳入的資料也對嗎？

主旨：延續同一摘要案例，必要工具被呼叫不代表參數與資料引用正確。

- 叫對 Builder 還不夠，要檢查參數和資料引用。
- Ref 是否對應本次分析結果？必要參數與使用條件是否正確？

接下一頁：這些驗收項目該怎麼判斷？前面介紹過程式與Judge，現在選用適合各項目的方法。

## 48｜驗收修改：哪些用程式，哪些用 Judge？

主旨：將入門頁介紹的評分方式落到這次修改的具體驗收項目；不要重複LLM Judge名詞定義，不把Judge當保證器。

- Builder呼叫、有效Ref、必要欄位等明確條件，驗收時用程式檢查。
- 摘要完整或證據支持程度等語意，依明確判準由Judge／人工輔助，並核對Judge是否可靠。

接下一頁：有了驗收方式，還要把真的踩過的坑留下來，讓每次修改都能重新檢查。

## 49｜踩過的坑，留進回歸測試

主旨：測試集由需求、真實失敗與補充邊界情境持續累積。

- 測試集從需求與 SOP 起步，持續加入真實失敗和邊界情境。
- 昨天踩過的坑要留在回歸測試，讓後續修改能自動檢查。

接下一頁：回歸測試也要有接受標準：同一情境要通過幾次，我們才接受這版修改？

## 50｜通過幾次，才接受這版修改？

主旨：前段已理解重跑的必要；這頁專講如何為候選Skill設定可接受門檻，並權衡風險與測試成本。

- 這裡進一步訂驗收門檻，不重複前段為什麼要重跑。
- 10次成功9次或5次全過只是不同示例，需依風險、情境與成本訂定；不能直接拿不同次數排名可靠性。
- 有限測試門檻不是執行保證，也不取代Guard。

接下一頁：這個失敗案例達到門檻了，其他原本會過的情境有沒有退步？

## 51｜修好一個問題，也可能弄壞其他情境。

主旨：Skill 修改可能影響原本通過的情境，接受修改不能只看原本的失敗是否修好。

- 修好一個失敗，其他原本通過的場景可能退步，要重跑回歸。
- 既然能驗證修改是否有效，就可以考慮讓 AI 協助寫與改 Skill。

接下一頁：有了驗證標準，就可以讓 AI 產生 Skill，再用測試判斷差距。

## 52｜從第一版 Skill 到功能完成，我沒有手寫過一行 Prompt。

主旨：人不必逐句手寫；開發用 AI 依需求產生候選 Skill，再依既定目標測試。

- 讓開發用 AI 讀 PRD、SOP 與程式碼，產生第一版 Skill。
- 用 Evaluation 找出實際行為與目標的差距；這個 AI 不是正式執行任務的 Agent。

接下一頁：測試沒有符合預期時，把執行紀錄交給 AI 分析並修改。

## 53｜Eval 的價值不是分數，而是讓 Skill 能被持續修正。

主旨：Evaluation 與執行紀錄提供可檢查回饋，驅動 AI 分析、修改 Skill、再驗證的循環。

- Evaluation 指出差距，Log 與 Trace 提供材料，讓 AI 分析並修改 Skill。
- 修完再跑回歸，符合接受條件才送審；不是無限盲目重試或只追分數。

接下一頁：人不再逐句撰寫，但仍然要定義成功與接受標準。

## 54｜人定義成功標準，修改用測試結果驗收

主旨：人掌握目標、情境與接受標準，AI 產生修改；候選版本用測試及紀錄驗收。

- 人定義成功標準、要測的場景與不可接受的風險；AI 產生候選修改。
- 不能為過關放寬標準，驗收要看修改差異、測試結果與對應紀錄。

接下一頁：這個循環會反覆進行，因此成本也要一起被觀察。

## 55｜每輪產生、測試與修正，都要留下成本紀錄

主旨：成本觀測涵蓋開發改進循環與正式執行，不是暗示 AI 寫 Skill 一定省錢。

- 成本包含 AI 讀紀錄、改 Skill、測試與回歸，也包含正式執行。
- 每輪記錄 Tokens、工具次數、重試與延遲，才能比較效果與代價。

接下一頁：回到一開始的 Tool Loop：讓它跑起來不難，讓它正確完成任務，才是我們一路處理的工程問題。

## 56｜寫出一個 Loop 很簡單，讓一個 Loop 能夠正確地完成任務，才是困難的工程問題。

主旨：回扣開場：工程難點不是啟動Tool Loop，而是讓它正確完成任務。

- 循環能運作，與任務能正確完成，是不同的事。
- Context、Skill、Evaluation、Guard與Trace，都是為了把任務做對。

接下一頁：模型會進步，也能幫忙解決其中一些問題；但能不能只等下一個更強的模型？

## 57｜解決這個問題，不能只靠最新的模型。

主旨：改善Agent不能只靠換模型；模型能力、任務設計與驗證需要一起考慮。

- 更好的模型能幫忙，但不是省略工程工作的理由。
- 模型選擇仍要放回任務、驗證與成本的條件一起考慮。

接下一頁：而且每次遇到問題都換更大的模型、塞更多Context、做更多重試，資源代價也會跟著增加。

## 58｜模型會越來越聰明，但是你的口袋沒有越來越深。

主旨：以口袋金句結尾：工程工作的理由，是在有限資源內把任務做對，而非一味增加模型與重試成本。

- 模型會持續進步，但工程仍要面對有限的資源。
- 前面的工作，是為了在資源限制下讓Agent正確完成任務。

接下一頁：分享結束，進入Q&A；不再追加另一句收尾金句。
